# Как участвовать в разработке ConsentKit

Спасибо за интерес к проекту. Здесь описано, как устроен репозиторий, что в нём
можно менять свободно, а что — только через юридическое ревью.

Проект распространяется под [GPL-2.0-or-later](LICENSE). Присылая изменения, вы
соглашаетесь опубликовать их на тех же условиях.

---

## 1. Структура репозитория

| Путь | Что там лежит |
|---|---|
| `SPEC.md` | Контракт проекта: инварианты, публичный API, границы файлов, история приёмок |
| `src/ck-core.js` | Ядро: состояние согласия, движок блокировки, storage, Google Consent Mode v2 |
| `src/ck-locales.js` | Словари локалей (`window.__ckLocales`), кроме встроенных en/ru |
| `src/ck-ui.js` | UI-слой в Shadow DOM: баннер, панель настроек, плавающая кнопка |
| `demo/` | Демо-магазин с фейковыми трекерами и панелью статуса |
| `npm/` | npm-обёртка: ESM/CJS-точки входа, React-хук, TypeScript-типы |
| `plugins/wordpress/consentkit/` | Плагин WordPress (PHP) со своей копией `src/` в `assets/` |
| `integrations/gtm/` | Пакет для Google Tag Manager: экспорт контейнера и инструкция |
| `tools/` | Сборщик инлайн-версии (`build-inline.mjs`) для конструкторов сайтов |
| `INSTALL.ru.md` | Инструкция по установке для не-программистов |
| `.github/workflows/` | CI: публикация демо на GitHub Pages |

Особенности, о которых легко забыть:

- **Порядок подключения контрактный:** `ck-core.js` → `ck-locales.js` → `ck-ui.js`
  → `ConsentKit.init(...)`. Ядро включает блокировку на parse-time, поэтому оно
  обязано грузиться первым и **без** `defer`/`async`.
- **`plugins/wordpress/consentkit/assets/` — побайтовые копии `src/`.** Меняете
  `src/` — синхронизируйте копии и проверяйте совпадение (`shasum`).
- **`demo/` ходит в ядро по относительным путям** (`../src/ck-core.js`), поэтому
  на Pages выкладывается корень репозитория, а не папка `demo/`.

## 2. Главное правило: инварианты GDPR неприкосновенны

Это не стилистические предпочтения, а то, из-за чего продукт вообще имеет смысл.
**Изменять их нельзя без юридического ревью** — даже если правка выглядит
безобидным улучшением UX или пары строк CSS.

1. **Равнозначность кнопок.** «Принять всё» и «Отклонить всё» — одинаковый размер,
   вес, контрастность и заметность. Отказ не может требовать больше кликов, чем
   согласие. Нельзя делать «Отклонить» ссылкой, серым текстом, мелким шрифтом или
   прятать его внутрь панели настроек.
2. **Отсутствие предвыбора.** Все opt-in категории (`functional`, `analytics`,
   `marketing`) по умолчанию `false`. Тумблеры в панели настроек не могут быть
   включены заранее. `necessary` всегда `true` и заблокирован — это единственное
   исключение.
3. **Тишина трекеров до согласия.** До явного выбора пользователя не выполняется
   ни один скрипт трекера, не ставится ни одна не-необходимая cookie, не уходит ни
   одного сетевого запроса на сторонние хосты. Это относится и к шрифтам, и к CDN:
   внешний запрос сам по себе передаёт IP посетителя третьей стороне.
4. **Отзыв не сложнее выдачи.** `withdraw()` доступен всегда через плавающую
   кнопку, чистит storage и известные cookie.
5. **Повторный запрос при смене политики.** Изменение `policyVersion` или
   истечение TTL сбрасывает состояние в `decided: false`.

Соответствующие пункты подробно описаны в `SPEC.md`. Если задача требует
отступить от любого из них — сначала обсуждение в issue с пометкой `legal`, и
только после письменного заключения юриста.

Отдельно: **никаких внешних ресурсов** в рантайме баннера — ни шрифтов, ни
иконок, ни аналитики самого баннера. Иконки — инлайновый SVG, шрифт —
`system-ui`.

## 3. Как гонять проверки

Зависимостей и сборки нет — всё проверяется штатным Node и браузером.

**Синтаксис JS:**

```sh
node --check src/ck-core.js
node --check src/ck-locales.js
node --check src/ck-ui.js
for f in npm/*.mjs npm/*.cjs; do node --check "$f"; done
```

**SSR-безопасность** (импорт в Node без DOM не должен падать):

```sh
node -e "import('./npm/core.mjs').then(() => console.log('ok'))"
```

**package.json:**

```sh
node -e "JSON.parse(require('fs').readFileSync('package.json','utf8')); console.log('ok')"
```

**GTM-контейнер:**

```sh
node -e "JSON.parse(require('fs').readFileSync('integrations/gtm/container-import.json','utf8')); console.log('ok')"
```

**PHP-плагин:**

```sh
php -l plugins/wordpress/consentkit/consentkit.php
php -l plugins/wordpress/consentkit/uninstall.php
```

**Синхронность копий ядра в плагине:**

```sh
for f in ck-core.js ck-locales.js ck-ui.js; do
  shasum "src/$f" "plugins/wordpress/consentkit/assets/$f"
done
```

**Демо в браузере** — обслуживать нужно с корня репозитория, иначе относительные
пути не разрешатся:

```sh
python3 -m http.server 8742
# затем открыть http://localhost:8742/demo/index.html
```

### Ручной смоук (обязателен для любых правок ядра или UI)

Прогоняется на демо, при открытой консоли и вкладке Application → Cookies:

1. **До выбора:** ни один трекер не загружен, ни одной `demo_*` cookie.
2. **«Принять всё»:** загрузились все три трекера, cookie появились.
3. **«Отклонить всё»:** не загрузилось ничего.
4. **Выборочно (только analytics):** загрузился только `ga.js`.
5. **Перезагрузка страницы:** выбор сохранён; смена `policyVersion` в init —
   баннер показывается снова.
6. **`withdraw()`:** `demo_*` cookie удалены, следующая загрузка чистая.
7. **A11y панели:** Esc закрывает, Tab не выходит за пределы панели,
   `role="dialog"`, `aria-modal`, у тумблеров `role="switch"` + `aria-checked`.

## 4. SPEC.md — это контракт, а не документация

`SPEC.md` описывает границы файлов, публичный API и инварианты. Он ведущий:
код следует за спецификацией, а не наоборот.

Порядок работы:

1. **Сначала читаем `SPEC.md` целиком**, включая дополнения (v0.2, v0.3, v0.4) и
   разделы «Приёмка» — там зафиксированы уже принятые архитектурные решения и
   причины, по которым что-то сделано именно так. Много «странностей» в коде
   объясняются именно этими записями.
2. **Не меняем публичный API молча.** Сигнатуры `ConsentKit.*`, имена событий
   `ck:*`, схема storage и имена dataLayer-событий — часть контракта. От них
   зависят WP-плагин, GTM-контейнер, npm-типы и чужие интеграции.
3. **Изменение контракта = сначала правка `SPEC.md`**, отдельным дополнением
   (новый раздел «Дополнение vX»), с обоснованием и критериями приёмки (DoD).
   Существующие разделы и записи о приёмках не переписываются — история решений
   сохраняется.
4. **Соблюдаем границы файлов.** У каждого модуля свой владелец и своя зона.
   Правка, размазанная по `src/`, `npm/` и `plugins/` сразу, — повод разбить её
   на части.
5. **PR ссылается на пункт спецификации**, который реализует или меняет, и
   перечисляет, какие пункты DoD прогнаны.

Если поведение кода расходится со `SPEC.md` — это баг в одном из двух, и в issue
нужно явно сказать, в каком именно, а не молча подгонять один под другой.

## 5. Стиль кода

- Vanilla JS (ES2020), ноль зависимостей, без сборщиков и транспиляции.
- Комментарии в коде — по-английски, лаконичные, объясняют «почему», а не «что».
- Документация для пользователей: `README.md` — английский, `INSTALL.ru.md` и
  `integrations/gtm/README.md` — русский.
- Никаких `eval` и динамической генерации кода — ни в JS, ни в PHP.
- В PHP: экранирование через `esc_*` на выводе, санитизация на входе, nonce на
  формах.
