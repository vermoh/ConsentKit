# Инлайн-сборка ConsentKit

`build-inline.mjs` собирает **один самодостаточный блок `<script>`**, который вы
вставляете в `<head>` сайта. Внутри блока — всё сразу: ядро согласия, движок
блокировки, интерфейс баннера, нужные языки и настройки. Никаких дополнительных
файлов загружать не нужно.

## Зачем это нужно

Жёсткие конструкторы сайтов — бесплатная Тильда, многие визитки и лендинги —
не дают положить на сайт свои файлы. Обычный путь в такой ситуации — подключить
баннер «из облака», ссылкой на чужой CDN.

Так делать не стоит. Как только браузер посетителя обращается к внешнему хосту,
он передаёт туда свой IP-адрес — **ещё до того, как человек что-либо разрешил**.
Именно за это штрафовали сайты в делах о Google Fonts: подгрузка шрифта с чужого
сервера сама по себе оказалась передачей персональных данных без основания.
С баннером согласия ситуация ровно та же, только нагляднее: инструмент, который
должен защищать приватность, первым же запросом её нарушает.

Инлайн-сборка снимает вопрос целиком: **ноль внешних запросов**. До согласия
посетителя со страницы не уходит ни одного обращения на сторонние хосты.

## Быстрый старт

Нужен установленный [Node.js](https://nodejs.org/) версии 16 или новее.
Проверить: `node --version`.

Откройте терминал в папке проекта ConsentKit и выполните:

```bash
node tools/build-inline.mjs --langs=ru,en --out=inline.html
```

Появится файл `inline.html`. Откройте его любым текстовым редактором,
скопируйте **всё содержимое целиком** (вместе со строками `<script>` и
`</script>`) и вставьте в `<head>` вашего сайта — как можно выше, лучше всего
первым же блоком.

> **Где это в Тильде:** Настройки сайта → Ещё → HTML-код для вставки внутрь HEAD.
> В других конструкторах ищите поле с названием вроде «Код в head»,
> «Custom HTML head» или «Пользовательский код».

Чем выше стоит блок, тем лучше: движок блокировки включается в момент разбора
страницы и успевает перехватить чужие скрипты только если стоит раньше них.

## Флаги

| Флаг | По умолчанию | Что делает |
|---|---|---|
| `--langs` | `en,ru` | Языки в сборке. `all` — все 34. |
| `--language` | `auto` | Язык баннера: `auto` (по языку браузера) или конкретный код. |
| `--layout` | `bar` | Вид: `bar` (полоса), `modal` (окно по центру), `box` (карточка в углу). |
| `--position` | зависит от вида | Для `bar`: `bottom` \| `top`. Для `box`: `bottom-right` \| `bottom-left`. |
| `--accent` | `#2B50D8` | Цвет кнопок, HEX. |
| `--mode` | `auto` | Тема: `auto` (как в системе у посетителя), `light`, `dark`. |
| `--policy` | `1` | Версия политики. |
| `--cookies` | — | Путь к JSON-файлу с описанием cookie. |
| `--no-branding` | — | Флаг без значения: собрать блок без брендинга совсем — без строки «Сделано в E-COM Consult» и без кода брендинга (−24 КБ). |
| `--out` | stdout | Куда записать результат. |
| `--help` | — | Справка. |

Справка на любом этапе: `node tools/build-inline.mjs --help`

### Про `--no-branding`

По умолчанию сборщик кладёт в конфиг объект `branding` со строкой-подписью:
«Сделано в E-COM Consult» для русскоязычных сборок и «Made by E-COM Consult»
для остальных, со ссылкой на ecomconsult.net. Флаг `--no-branding` убирает
объект целиком — подписи в баннере не будет, — и вдобавок не кладёт в сборку
`src/ck-ui-branding.js`, поэтому блок худеет примерно на 24 КБ.

```sh
node tools/build-inline.mjs --langs=en,ru --no-branding --out=inline.html
```

Никаких обязательств тут нет: клиент под лицензией MIT, подпись убирается одним
флагом (или удалением объекта `branding`, если вы пишете конфиг руками). В
платном сервисе отключение подписи входит в платные тарифы — но платят там за
хостинг, кабинет и сканирование, а не за саму строку.

Язык подписи определяется сборкой, а не машиной: при `--language=ru` (или
`--language=auto`, когда `ru` стоит первым в `--langs`) подпись русская, иначе
английская. Поэтому все блоки `ru-*` в `ready/` идут с русской строкой, а
`en-bar` и `eu-bar` — с английской.

Строка весит около 200 Б. Логотип по умолчанию **не** добавляется: файл
`brand/ecom-consult-logo.svg` — белый леттеринг для тёмного фона, на светлой
подложке баннера он был бы не виден (подробности — в комментариях к
`buildBrandLogo` в `src/ck-ui.js`). Свой логотип можно передать через
`branding.logo` и `branding.logoDark` в собственном конфиге.

Флаг `--no-branding` убирает и объект из конфига, и **сам код брендинга**:
он живёт в отдельном файле `src/ck-ui-branding.js` (~23 КБ) и просто не
попадает в сборку. Экономия — около **24 КБ** на блок. Без этого файла
`ck-ui.js` не рисует ни логотип, ни подпись и ничего не ломает: расширение
необязательное по устройству (было долгом Д11, закрыт в 0.3.6).

### Про языки

`en` и `ru` встроены в интерфейс ConsentKit и **не занимают места**. Поэтому при
`--langs=en,ru` (и при `--langs=en` или `--langs=ru`) блок локалей в сборку не
включается вовсе — сборка получается самой лёгкой.

Доступны 34 языка: bg, ca, cs, da, de, el, en, es, et, fi, fr, ga, hr, hu, is,
it, lt, lv, mk, mt, nb, nl, no, pl, pt, ro, ru, sk, sl, sq, sr, sv, tr, uk.

**По умолчанию язык выбирается автоматически** — по языку браузера посетителя.
Если вы собрали `--langs=de,fr`, то немец увидит немецкий, француз —
французский, а, скажем, испанец — английский (запасной вариант, он есть всегда).
Класть в сборку язык «на всякий случай» не нужно: каждый лишний язык — это
лишние килобайты на каждой загрузке страницы.

**Если сайт на одном языке**, автоопределение обычно только мешает: посетитель
с английским браузером увидит английский баннер на русском сайте. Зафиксируйте
язык флагом `--language`:

```bash
node tools/build-inline.mjs --langs=ru --language=ru --out=inline.html
```

Язык из `--language` обязан входить в `--langs` — иначе сборщик остановится и
подскажет, что добавить. Так нельзя случайно собрать блок, который молча
переключится на английский.

### Про версию политики

`--policy` — это номер версии вашей политики использования cookie. Пока номер
не меняется, посетитель, однажды сделавший выбор, баннер больше не видит.

**Поднимите номер (`--policy=2`, `3`, …), когда меняете смысл политики:**
добавили новый сервис аналитики, сменили рекламную сеть, изменили состав
собираемых данных. Тогда все посетители увидят баннер заново и примут решение
уже про новую редакцию. Это требование GDPR: согласие даётся на конкретный
объём обработки, и при его расширении прежнее согласие не действует.

### Про таблицу cookie

Файл для `--cookies` — обычный JSON-массив. Эти записи посетитель увидит в
панели «Настроить», раскрыв нужную категорию.

```json
[
  {
    "name": "_ga",
    "category": "analytics",
    "vendor": "Google",
    "purpose": "Считает визиты и просмотры страниц.",
    "expiry": "2 года"
  },
  {
    "name": "_fbp",
    "category": "marketing",
    "vendor": "Meta",
    "purpose": "Отмечает посетителя для показа рекламы.",
    "expiry": "3 месяца"
  }
]
```

`category` — одно из: `necessary`, `functional`, `analytics`, `marketing`.
Поля `name` и `category` обязательны, остальные — по желанию.

## Примеры

Минимальная сборка, русский, румынский и английский, полоса внизу:

```bash
node tools/build-inline.mjs --langs=ru,en --out=inline.html
```

Карточка в правом нижнем углу, тёмная тема, свой цвет, три языка:

```bash
node tools/build-inline.mjs --langs=de,fr,pl --layout=box --mode=dark \
  --accent=#0A7A5C --out=inline.html
```

Окно по центру, все языки, вторая редакция политики, со списком cookie:

```bash
node tools/build-inline.mjs --langs=all --layout=modal --policy=2 \
  --cookies=my-cookies.json --out=inline.html
```

Вывод в конвейер (сам HTML идёт в stdout, сводка — в stderr):

```bash
node tools/build-inline.mjs --langs=en | pbcopy
```

24 КБ, потому что вместе с объектом `branding` из сборки уходит и файл
`src/ck-ui-branding.js`.

### Отладка

Самой панели отладки в блоке нет. В него входит только загрузчик
`src/ck-debug-loader.js` — около 5,1 КБ, — а сама панель (`src/ck-debug.js`,
около 33 КБ) подгружается с CDN и только тогда, когда кто-то откроет страницу
с `?ck_debug=1`. Без этого флага загрузчик не создаёт ни одного узла DOM, не
ставит наблюдателей и **не делает ни одного сетевого запроса**.

Адрес панели загрузчик выбирает так, побеждает первое совпадение:

1. `window.ConsentKitDebugUrl`, если вы его задали, — своя копия или зеркало;
2. `<API_BASE>/client/ck-debug.js`, если на странице есть `ck-saas.js`
   с идентификатором сайта (`API_BASE` — его `data-ck-api`). SaaS-развёртывание
   обязано отдавать панель по этому пути;
3. jsDelivr, привязанный к версии работающего ядра:
   `https://cdn.jsdelivr.net/npm/@ecomconsult/consentkit@<версия>/src/ck-debug.js`.

Версия берётся из `ConsentKit.version`, поэтому панель никогда не окажется
новее или старее клиента, о котором она отчитывается. Подробности —
в README, раздел «Debug mode».

Код не сжимается минификатором намеренно: блок вставляется в чужую страницу,
и возможность открыть его и прочитать глазами важнее экономии. При включённом
на сервере gzip реальная передача выходит примерно в три-четыре раза меньше.

Берите только те языки, которые действительно нужны вашей аудитории.

## Как пересобрать после обновления ConsentKit

Сборка **статична**: это снимок кода на момент запуска команды. Обновление
ConsentKit само по себе на уже вставленный блок никак не влияет — исправления
и новые возможности до сайта не доедут, пока вы не пересоберёте блок вручную.

Порядок действий:

1. **Обновите исходники.** Скачайте новую версию ConsentKit (или `git pull`,
   если работаете с репозиторием). Меняются файлы в папке `src/`.
2. **Найдите прежнюю команду.** Она записана в шапке самого блока — в комментарии
   в первых строках, вместе с версией и датой сборки:

   ```
   /* ConsentKit — инлайн-сборка. Вставьте весь этот блок в <head> сайта.
    *
    * Версия ConsentKit: 0.3.0
    * Дата сборки:      2026-08-27
    * ...
    * Файл собран автоматически — правьте не его, а исходники и пересоберите:
    *   node tools/build-inline.mjs --langs=ru,en --layout=bar ...
    */
   ```

   Скопируйте команду из этой строки — в ней уже зафиксированы все ваши
   настройки, включая те, что брались по умолчанию.
3. **Выполните её заново** в обновлённой папке проекта.
4. **Замените блок на сайте** новым содержимым файла — целиком, старый удалите.
5. **Проверьте на сайте:** откройте страницу в режиме инкогнито (чтобы не мешало
   ваше прежнее согласие) и убедитесь, что баннер появился и кнопки работают.

Проверить версию, из которой собран блок, можно в его шапке. Версия берётся
не из README и не из `package.json`, а прямо из кода ядра при сборке — так в
комментарии всегда стоит то, что действительно попало внутрь.

> **Важно:** не правьте содержимое собранного блока «по месту» — любая правка
> потеряется при следующей пересборке. Всё, что нужно изменить, задаётся флагами.

## Если что-то пошло не так

**Баннер не появляется.** Скорее всего, вы уже дали согласие на этом сайте
раньше — ConsentKit его запомнил. Откройте страницу в режиме инкогнито.
Либо поднимите `--policy` и пересоберите.

**Ошибка `node: command not found`.** Node.js не установлен — поставьте с
[nodejs.org](https://nodejs.org/), затем закройте и откройте терминал заново.

**Ошибка про `src/ck-core.js`.** Команда запущена не из папки проекта.
Перейдите в папку ConsentKit (`cd путь/до/consentkit`) и повторите.

**Цвет не применяется / ошибка про HEX.** В некоторых оболочках символ `#`
начинает комментарий. Возьмите значение в кавычки: `--accent="#2B50D8"`.

**Конструктор «съедает» или ломает код при вставке.** Убедитесь, что вставляете
в поле для HTML-кода в `<head>`, а не в текстовый блок страницы: визуальные
редакторы экранируют теги и превращают код в текст.

## Для разработчиков

Несколько решений, заметных при чтении кода сборщика:

- **Локали фильтруются исполнением, а не разбором текста.** `src/ck-locales.js`
  выполняется в изолированном контексте `node:vm` с заглушкой `window`, после
  чего из него берётся объект `__ckLocales` и нужные ключи сериализуются через
  `JSON.stringify`. Разбирать этот файл регулярными выражениями нельзя: он не
  предназначен для парсинга, и любая правка форматирования сломала бы такой разбор.
- **Экранирование `</script`.** Итоговый текст попадает внутрь HTML-элемента
  `<script>`, а HTML-парсер закрывает этот элемент на первой же
  последовательности `</script` — независимо от того, что она стоит внутри
  строки или комментария JavaScript. Поэтому во всём собранном тексте
  (код, комментарии, JSON таблицы cookie) `</script` заменяется на `<\/script`
  без учёта регистра. Для JavaScript это та же самая строка, для HTML —
  уже не признак конца элемента. Заодно экранируются U+2028/U+2029.
  Перед записью файла сборщик ещё раз проверяет результат и отказывается
  писать блок, если последовательность каким-то образом уцелела.
- **`init()` вызывается после готовности DOM** — страховка, чтобы блок
  одинаково работал независимо от места вставки: вызов обёрнут в проверку
  `document.readyState` с подпиской на `DOMContentLoaded`. Само по себе это не
  обязательно — `mount()` в `ck-ui.js` уже откладывает монтирование, если
  `document.body` ещё не существует. На блокировку задержка не влияет: движок
  ядра включается при разборе скрипта, до `init()`.
- **Порядок склейки** — контрактный: ядро → локали → интерфейс → `init()`.
  Файлы соединяются через `\n;\n`, чтобы автоматическая подстановка точки с
  запятой не склеила соседние IIFE.
- **Сводка идёт в stderr**, сам HTML — в файл или stdout, поэтому вывод можно
  безопасно направлять в конвейер.

Самопроверка сборщика (три варианта, `node --check` на извлечённом
экранированном коде, отсутствие `</script`, запуск в браузере с блоком в
`<head>`) описана в SPEC.md, раздел A дополнения v0.4.

# Экспорт базы трекеров в плагин WordPress

`export-hostdb.mjs` переносит `HOST_DB` и `PATH_DB` из `src/ck-core.js` в
`plugins/wordpress/consentkit/includes/hostdb.php`, откуда их читает серверная
разметка плагина (долг Д10).

```bash
node tools/export-hostdb.mjs            # записать файл
node tools/export-hostdb.mjs --check    # только проверить: код 1, если устарел
node tools/export-hostdb.mjs --stdout   # напечатать, ничего не записывая
```

**Зачем.** Плагин размечает теги трекеров на сервере, а тот же клиент потом
работает с ними в браузере. Если таблицы разойдутся, сервер и браузер начнут
считать один и тот же хост разными вещами — на одной и той же странице.
Единственный источник правды — `src/ck-core.js`; PHP-файл генерируется и
помечен «не редактировать». Расхождение ловит `test/hostdb.test.mjs` в
`npm test`.

**Почему исполнением, а не разбором текста.** `HOST_DB` — приватная переменная
внутри IIFE ядра, в `window.ConsentKit` она не попадает, поэтому загрузить ядро
(как это делает `test/version.test.mjs`) недостаточно. Литерал находится
подсчётом скобок и отдаётся движку JavaScript через `node:vm`. Вытаскивать
пары ключ-значение регуляркой нельзя: почти на каждой строке идёт хвостовой

Экспортёр отказывается писать файл, если извлёк подозрительно мало записей
(меньше 40 хостов) или встретил категорию не из четырёх известных: пустая
таблица — это плагин, который ничего не блокирует, но при этом рапортует об
успехе.
